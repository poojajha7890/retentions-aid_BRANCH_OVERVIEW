§7 · Local DB with Docker + daily server sync

Production DBs change daily. This section shows how to keep a local Docker Postgres in sync — with 4 different strategies, their trade-offs, and the recommended one.

🚫 Patient data. The schema holds patients, appointments, and insurance fields. Treat every prod dump as protected health information. Mask PII columns on the server before the file ever leaves it, never commit dumps, never place them on shared drives.

7.1 · Why a daily sync is needed

The app stores one PostgreSQL database per clinic. Local development against a stale snapshot breaks as soon as reports, cron jobs, or alerts reference rows that don't exist locally yet. A daily pull keeps developers working against near-live data without touching production.

ℹ️ Two sync surfaces exist. (a) Data — the clinic DBs, pulled daily by dump + restore. (b) Schema — the tables/triggers, loaded once from create_tables_and_triggers.py on an empty DB. Data restore handles schema too, so the schema loader (§5c) is only needed when a developer starts from a truly empty local DB.

7.2 · Four ways to set up the local DB

Pick one. All four end with a working local Postgres on localhost:5432; they differ in effort, freshness, and how much patient data moves.

Option A · Manual one-shot dump + restore Effort: Low · Freshness: stale
Setup
Developer SSHes to the VPS, runs pg_dump, copies the file down with scp, and restores it into the local container once.
Best for
Onboarding a new developer, or one-off debugging against a specific snapshot.
Impact
Zero automation. Data goes stale the moment the server runs its next write. Every refresh is a manual 5-minute dance.
Risk
Low — no automation, no secrets stored, no cron.
Option B · Cron on VPS + scheduled pull on laptop Effort: Medium · Freshness: 24 h
Setup
Server runs pg_dump every night at 02:00 via cron. Each developer machine runs a scheduled task at 03:00 that pulls the newest dump with scp (or rsync) and restores it into the local container.
Best for
Small teams; developers work at their desk with predictable morning-fresh data.
Impact
Data at most 24 h old. Requires SSH access from each laptop to the VPS. Works offline once pulled.
Risk
Medium — SSH key on each laptop, credentials scoped to a read-only DB user, dump file sits on disk until the next pull overwrites it.
Option C · Cloud bucket relay (S3 / Backblaze / Drive) Effort: Medium · Freshness: 24 h
Setup
Server cron dumps and uploads to a private bucket with aws s3 cp (or rclone). Developers pull with aws s3 sync from their laptop — no direct SSH needed.
Best for
Teams that want to avoid granting each laptop SSH access to the production VPS, or developers on networks that block port 22.
Impact
Same 24 h freshness as Option B, plus versioning/retention on the bucket and audit logs of who downloaded what.
Risk
Medium — bucket must be private, encrypted at rest, lifecycle-expire after 7 days. Each developer gets a scoped read-only key, not the server's write key.

⚠️ Encryption & retention. Enable SSE on the bucket, restrict with an IAM policy limited to s3:GetObject on that prefix, and set a lifecycle rule deleting objects after 7 days. Log bucket access.

Option D · Direct tunnel — developer queries the live DB Effort: Low · Freshness: live
Setup
An SSH tunnel forwards localhost:5433 → vps:5432. Backend .env points at localhost:5433. No dump, no container.
Best for
Read-only exploration, debugging a specific production row.
Impact
Always fresh — but every query hits production. A developer running an expensive report slows the production server for real users.
Risk
High — do not use for day-to-day development. Accidental writes go straight to prod; connection storms from local testing can exhaust the server's pool; no PII masking between dev and prod.

🚫 Never use Option D with the production credentials. If you must tunnel, tunnel as dev_readonly, never as the app user. Prefer Option B or C for anything longer than a single debugging session.

7.6 · Safety rules (all options)

  • Mask PII on the VPS, before the file leaves it. Never rely on the laptop to mask.
  • Read-only DB role for all backups. backup_ro has SELECT only.
  • Dumps never enter git. Add docker/dumps/, docker/db_data/, *.sql at the repo root level to .gitignore.
  • Retention: delete dumps older than 7 days on both the server and the laptop.
  • Dev Firebase only. GOOGLE_APPLICATION_CREDENTIALS must point at a dev project. Never copy production Firebase credentials to a laptop.
  • Bucket hygiene (Option C): private bucket, SSE enabled, IAM limited to s3:GetObject on the dump prefix, lifecycle rule 7 days.
  • Never use Option D with the app's production credentials — only dev_readonly, and only for short lookups.

7.7 · Windows setup — 5 ways to run the whole project locally

Production server is Windows, so Docker Desktop won't run on it — but every developer machine (Windows 10/11) can. Pick one of the five approaches below. All of them reach the same end state: a local Postgres on localhost:5432, a Flask API on localhost:8000, and a React UI on localhost:3000.

Way 1 · Docker Desktop + WSL 2 backend (recommended) Effort: Low
What
Install Docker Desktop for Windows with the WSL 2 backend. Run every service — Postgres, Flask, React — as Linux containers. No native Python/Node install on the host.
Why
Identical behaviour to production Linux containers, one command to start everything, cleanest to onboard a new developer.
Where
Host prerequisites: Windows 10 2004+ or Windows 11, WSL 2 enabled, virtualization enabled in BIOS. Then Docker Desktop installs WSL distro docker-desktop.
Impact
Everything runs in containers. Host stays clean. Slight disk overhead (~2 GB per image). Perfect for CI parity.
Risk
Low. Main gotcha is the WSL 2 memory ceiling — configure .wslconfig if the machine has < 8 GB RAM.
Way 2 · Docker Desktop — DB in Docker, API & UI natively on Windows Effort: Low
What
Postgres runs in a Docker container. Flask and React run directly on Windows using conda and Node — the same way they run today on the VPS.
Why
Debugging is easier (native debugger, no container rebuilds), and it's the least-change path from how the team already works.
Where
Docker Desktop for the DB only; conda create -n retentions-aid python=3.11; Node 16+ from winget install OpenJS.NodeJS.LTS.
Impact
Fastest iteration on backend code — Flask's auto-reload works immediately. DB still isolated. Downside: host must have Python + Node installed, so "works on my machine" risk returns.
Risk
Low. Only friction is a firewall prompt the first time Flask binds port 8000.
Way 3 · WSL 2 Ubuntu — everything inside Linux, no Docker Desktop Effort: Medium
What
Install Docker Engine inside a WSL 2 Ubuntu distro. Run the entire stack from a Linux shell. No Docker Desktop licence needed.
Why
Free for commercial use, lower memory footprint than Docker Desktop, closest to a Linux dev experience without leaving Windows.
Where
wsl --install -d Ubuntu → inside Ubuntu: curl -fsSL https://get.docker.com | sh → add user to docker group.
Impact
Two shells (Windows for VS Code, WSL for docker + git). All Linux-native: paths like /mnt/d/retentions-aid. Line-ending issues disappear because git runs inside Linux.
Risk
Medium — no Docker Desktop GUI, no automatic updates, you maintain the engine. Enterprise machines may block wsl --install.

ℹ️ File performance tip: keep the repo inside the WSL filesystem (~/retentions-aid) rather than /mnt/d/... — file I/O is 3–5× faster there. Use Windows Explorer's \\wsl$\Ubuntu\home\you\retentions-aid to browse files from Windows.

Way 4 · Windows Containers — everything Windows-native Effort: High · 🚫 not recommended
What
Run Windows Server Core containers instead of Linux ones, using the Windows container mode of Docker Desktop.
Why
Theoretically matches the Windows production server. In practice nothing else here works well.
Where
Docker Desktop → switch to "Windows containers". Postgres image must be a Windows build; the Python images need Windows base OS layers.
Impact
Very negative. Official Postgres and Python "Windows" images are huge (2–6 GB each), slow to start, poorly maintained, and don't match what production actually runs.
Risk
High. Breaks psycopg2 wheels, breaks Gunicorn (not Windows-native), breaks your Dockerfiles. Do not pursue.

🚫 Why we don't do this: production already runs native Windows Postgres + conda + Gunicorn-under-WSL. Introducing Windows containers adds a third environment that matches neither the current server nor the recommended local setup. It's the worst of both worlds.

Way 5 · No Docker at all — native Windows Postgres + native Python/Node Effort: Medium
What
Install PostgreSQL natively on Windows (the same installer the VPS uses), install Python via conda, run the app exactly as today. Skip Docker entirely.
Why
No Docker licence issue, no WSL, smallest learning curve for developers who already know this stack. Matches production 1:1.
Where
winget install PostgreSQL.PostgreSQL.15 · winget install Anaconda.Miniconda3 · winget install OpenJS.NodeJS.LTS. Then pg_restore the dumps into the native instance.
Impact
Multiple native services running on each laptop, port conflicts when someone has two projects, no isolation between dev and personal Postgres instances. Fresh-clone setup takes 30–60 min vs 5 min with Docker.
Risk
Medium — hard to reproduce exactly across machines because Windows Postgres versions/patches drift.

7.12 · Recommendation

✅ For this team, use Way 1 — Docker Desktop + WSL 2 with the full stack in containers.

  • Reproducible across every Windows 10/11 developer machine.
  • One command to start: docker compose up -d.
  • Same container images will deploy identically in CI or any future Linux host.
  • Production server stays as-is (native Windows) — Docker is local only, never installed on the VPS.

Fallback: if Docker Desktop is blocked by corporate policy (licence or IT), use Way 3 (WSL Ubuntu + Docker Engine) — same result, no Desktop dependency.

⚠️ Docker Desktop licensing. Free for personal use, education, and companies with fewer than 250 employees AND less than $10M annual revenue. Larger organisations need a paid subscription. If in doubt, go with Way 3.

7.13.4 · Laptop side — pull at 09:00 and restore

✅ End state. Every weekday morning around 09:00, each developer's laptop Docker Postgres contains the same masked data that production had at 08:30. No manual work, no direct connection from laptop to production, no patient data leaks.

7.13.6 · Timing, failures, and safe-guards

ConcernHandling
Server dump slower than usualLATEST.done marker only written after every clinic dump succeeds; laptop waits for it.
Laptop offline at 09:00Task Scheduler runs at next logon (StartWhenAvailable) → catch-up automatically.
Dump half-copiedOnly restore files ending .sql that match the *.done marker's date. Optionally checksum with Get-FileHash.
Restore fails midwayRestore uses DROP DATABASE IF EXISTS first; the pg_dump output recreates it. If it fails, no partial data — the DB is simply absent until next run.
Developer wants yesterday's dataKeep 7 days of dumps; the restore script can pick a specific file. Add -Date 2026-10-03 parameter.
Disk growth on laptopKeep last 3 dumps only: Get-ChildItem ... | Sort LastWriteTime -Desc | Select -Skip 3 | Remove-Item.
Docker daemon not runningIn sync.ps1, check docker info; if it fails, print "Start Docker Desktop" and exit 1.

7.13.7 · What never to do

  • Never point a laptop's Flask .env at the production server. Always localhost:5432.
  • Never use the app's production Postgres user for dumps — only backup_ro.
  • Never skip PII masking because "it's only one dump". It's still PHI.
  • Never commit dumps to git. docker/dumps/ is in .gitignore.
  • Never install Docker on the production Windows Server — Docker Desktop does not support Windows Server as a host and it would destabilise production.

ℹ️ One-sentence summary: Server dumps and masks at 08:30 → publishes to a shared folder / SFTP / bucket → each laptop pulls at 09:00 and restores into a local Docker Postgres. Local DB mirrors production daily without ever touching the production server's database directly.
